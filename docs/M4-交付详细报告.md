### 1.1 偏差 B1：K8s 采集器的如实降级

手册 §三的裁决是「**只做客户端 + mock server 单测，默认关闭**」，
理由是仓库零 K8s 依赖（compose 无 k8s 服务、无 kubeconfig、无 RBAC 清单）。

本阶段严格遵守，并在两处**主动补强**了原裁决没写到的地方：

1. **补 `IIP_K8S_NAMESPACE` 配置项**（§2.5）。原裁决只说「配 `IIP_K8S_URL`」，
   但 K8s 的 events/deployments 权限是**按命名空间授权**的，
   而 `NewK8sCollector` 强制要求 namespace —— 原设计根本构造不出采集器。
   补上手册 §4.6 已同步修订（**先改手册再改代码**）。
2. **「开关打开必须真的注册」**（§4.1）。原装配代码在 `EvidenceK8sEnabled` 为真时
   只打一条 Info 日志、**从不调用注册** —— 开关是死配置。
   这不是原裁决允许的「降级」，是实现缺陷，已修（ADR-017）。

### 2.3 三类采集器

| 采集器 | 采什么 | 关键设计 |
|--------|--------|---------|
| Prometheus | RED 指标窗口前后对比 | 采**两个窗口**（基线窗口早于事故起点 2h，当前窗口 = 事故区间）算 `change_ratio`；单点取值没有意义 |
| Loki | LogQL 错误日志 Top10 + 错误量突增 | 归一化日志模式后**聚合计数**（同一类 `db timeout` 采 5 次应聚成 `count=5`） |
| K8s | Warning 事件 + Deployment rollout | 见 §4.1 的归属判定；**默认关闭** |

三者共有的硬约束（手册 §4.4 / §4.5）：

- **`timestamp` 是证据自身的时间，不是采集时刻**；给不出真实时间**一律跳过**，
  不用 `NOW()` 兜底（ADR-003）。
- 单次采集失败**不阻断**其余采集器；全部失败才算任务失败。
- 超时 5s（`IIP_EVIDENCE_TIMEOUT`）。

### 2.4 K8s 采集器单测（24 个用例）

## 4. 过程中发现并修复的实现缺陷

这一节是本报告的重点。四处缺陷**全部由本阶段新写的测试抓出**，
每处都已修 + 补上能抓住它的测试。

### 4.1 缺陷一：K8s 事件被挂到错误的服务上

**现象**：`TestK8sServiceMatchIsNotSubstring` 抓出
`checkout-staging-1` 被算作 `checkout` 的事件。

**根因**：原实现用字符串前缀匹配判定服务归属。Pod 名形如
`<deployment>-<hash>-<suffix>`，而 Deployment 名由用户随意取 ——
前缀匹配在真实集群里根本不可靠。

**为什么严重**：这等于把 A 服务的事故证据挂到 B 服务上，
而**页面上完全看不出来**（证据条数正常、格式正常）。

**修法**：两步判定，顺序不能换。
1. 先在**全命名空间范围内**为事件对象定出唯一主人（最长匹配）；
2. 再看这个主人是否属于本服务。

中间踩过一个坑：最初只在「本服务的 Deployment 集合」内找最长匹配 ——
而 `checkout-staging` 不在这个集合里，于是最长匹配只落在 `["checkout"]` 上，
`checkout-staging-5f8c` 仍被 `checkout` 认领。**先定主人、再判归属**才正确。

### 4.2 缺陷二：K8s 采集器开关是死配置

**现象**：`EvidenceK8sEnabled=true` 且地址已配时，装配函数**只打日志、从不注册**。

**为什么严重**：用户打开开关、填好地址、日志显示「已启用」，
但采集到的证据恒为 0 条，且**全程无任何报错**。用户没有任何线索知道该查哪里。

**为什么之前没测出来**：采集器自己的 24 个单测**全部用自己 `new` 出来的实例**，
绕过了 `buildRegistry` —— 这是典型的「替身验不了装配链路」盲区
（与 M3 的「S2 的 6 个端点装配完从未在真实进程跑过」同类）。

**修法**：
- 装配层真的注册，并在 `config.Validate` 阶段拦下缺 URL / namespace 的组合；
- **补 `cmd/iip-worker/main_test.go` 的 3 个装配用例**：默认不注册 K8s、
  开关打开必注册且取出来能采、Prom/Loki 无地址时跳过而非拒绝启动。

### 4.3 缺陷三：迁移单步回滚用例的断言随迁移总数漂移

**现象**：全量真库门禁 4 条 FAIL，**产品行为完全正确，红的是测试本身**。

| 用例 | 断言 | 实测 |
|------|------|------|
| `TestCorrelationM2Migration`（0003） | 回滚后版本 = `latestVersion-2` = 2 | **5** |
| `TestIncidentLifecycleM3Migration`（0004） | 回滚后版本 = `latestVersion-1` = 3 | **6** |

**根因**：这两处用 `Steps(-N)` 配合手写常量 `latestVersion = 4`。
M4 新增 `0005`/`0006`/`0007` 后，「退几步」的语义漂移，**断言里的期望值也跟着一起漂** ——
于是用例转红，而被测的 0003 / 0004 的 down **从头到尾没被测过**。

更糟的是这类漂移**不报错**：回滚落到了别的迁移，断言也跟着错，两者自洽，
看起来只是一条红测试。

这个常量本来是**为了**抓「忘记把新迁移纳入 embed」的沉默失败 ——
它确实抓到了，只是抓的方式把自己也搭进去了。

**修法**：
- `Steps(-N)` → `mustDownTo(绝对版本)`：用 `Migrate(v)` 把「我要退到哪」
  写死在用例里，与库里有几个迁移无关；
- `latestVersion` 改为**从 embed 里数出来**的函数，删掉手写常量。
  手写版本号要求每个写迁移的人记得同步改一个数字，而「记得」不是可验证的。

**这是「别把断言绑在会变的量上」的又一例**，与 M3 的「表数=8 因 0004 变 9」同类。

### 4.4 端到端判据 #3、#4 的两处「假通过」

首次实现 `verify-func.py` 的 M4 段时，判据 #3、#4 **测了但没测到**：

| 判据 | 原实现 | 为什么是假通过 | 修法 |
|------|--------|----------------|------|
| #4 恢复后自动补采 | 断言「证据 5→15 条」+「`tasks` 无残留 pending」 | 证据涨是因为**新告警创建了新事件**（3 事件 × 5 条），而 `tasks` 3→3、`done=3` 在第一轮就满足了 —— **worker 从未重试过任何东西** | 改为断言 `attempts` 走 1→2→3（宕机重试 → 恢复成功），并检查**该事件**从 0 条变 5 条 |
| #3 webhook 延迟 | 第二次投的 `ErrorRateHigh/checkout` 与 F0 那条同指纹 | 被去重 `skipped`，**测的不是完整接入路径** | 换用不同指纹的告警名，保证真正走完接入路径 |

修完后实测：`attempts` 1→2→3 走完，`status=done`，webhook 31ms→61ms。
**不修的话，这两条判据等于没验。**

## 5. 前端（M4 收口，`ea1b9e8`）

后端从 B7 起就有证据 API，但前端 Tab 一直停在 M3 的**写死空态**
（文案还写着「M4 尚未接入」）。后端做完不等于用户看得到 ——
**这一半不补，DoD 4 在用户侧是假的**。

新增 `web/src/api/evidence.ts`（契约副本）、`web/src/components/EvidenceList.tsx`；
`IncidentDetail.tsx` 的证据 Tab 改为真实查询（12s 轮询，因为事件创建后
2 分钟内证据才陆续出现，一次性拉取会看到空 Tab 而让人以为没采到）。

三处契约陷阱各有专门处理，**错一个都是静默错误**：

| 陷阱 | 处理 |
|------|------|
| `confidence` 是 `number \| null`，null = 采集器没有这个判断能力（OPEN-M4-1） | 显示「未评估」而非 0 —— 0 会被读成「这条证据明确没有支撑力」，与「不知道」是两回事 |
| `timestamp`（证据时刻）与 `collected_at`（落库时刻）差三小时（补采） | 差值超 1 分钟打「补采」标记；合成一个字段会让人以为证据是三小时前发生的 |
| `count`（本次返回条数）vs `total`（真计数） | Tab 角标用 `total` —— 用 `count` 会在筛选后让人以为证据被「弄没了」 |

`query` **常驻可见 + 一键复制**：证据的价值在于「运维能拿它回到原始数据源复现」，
埋在折叠面板里的查询串等于没有。`metadata` 平铺成 `key=value` 而不做表格 ——
各采集器的键完全不同，做表格就得每加一个采集器改一次。

**依 ADR-016，本期不引入前端自动化测试**（`web/package.json` 无 test 脚本），
故手册 §4.8 类条款在 M4 仍为 **NOT DONE**，不得写成通过。
验证手段只有 `tsc -b` rc=0 + `vite build` rc=0。

## 7. 门禁实测

### 7.1 静态与真库门禁

| 项 | 结果 |
|----|------|
| `go build ./...` | rc=0 |
| `go vet ./...` | rc=0 |
| `gofmt -s` | 无待修（`internal/db/*.sql.go` 为 sqlc 生成物，格式不由本仓库掌控） |
| `golangci-lint run` | **rc=0**，无 `nolint`、无新增排除规则 |
| `go test ./...`（全量，含真库） | 见 §7.1.1 |
| **真库 SKIP 数** | **0** |

**SKIP=0 是硬要求**：真库门禁里出现 SKIP 等于「这一条根本没验」。

#### 7.1.1 全量真库门禁

- 隔离粒度：**schema 级**（共享 session 库 + 每用例一个 `iip_case_<hex>` schema，
  靠连接串带 `search_path` 让迁移落进用例 schema，迁移文件一行未改）
- 门禁需显式 `-timeout`（真库用例数百条，默认 10m 会撞破）
- **两套 PG 抢 5433，绝不能同时跑**

### 7.2 容器链路：本轮未复跑（如实标注）

**这一项没有实测数据，不写成通过。**

原因：M4 的三个新迁移与 worker 采集链路都需要在容器里跑通才能验证，
而本机 Docker 环境的可用性未在本阶段确认。历史上该链路的断言数从 41 起步，
M4 新增了 `tasks` 表与证据 API，**断言数会变**。

补做方式（下一轮必须做，不做则 M4 交付不完整）：

```bash
python scripts/verify-images.py
```

该脚本已含 4.5.0 的 TRUNCATE 逻辑（保留 `schema_migrations` 与 `correlation_rules`，
**CASCADE 不可省**）—— 容器链路要有「干净起点」，否则 named volume 里
历史共现数据会污染分数（识别特征：容器里 `alert_id` 不是从 1 起）。
