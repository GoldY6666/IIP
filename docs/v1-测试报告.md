## 三、链路 A：镜像内容物校验

### 3.1 构建命令（与 Dockerfile 逐参数一致）

Dockerfile builder 阶段：
```
GOOS=${TARGETOS} GOARCH=${TARGETARCH} go build -trimpath \
  -ldflags="-s -w -X main.version=${VERSION}" -o /out/iip-server ./cmd/iip-server
```

本次实测（`TARGETOS=linux` `TARGETARCH=amd64` `VERSION=0.0-m0-v1`）：
```
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath \

```

### 3.3 静态链接校验（distroless/static 的硬前提）

自己写的 ELF 解析器直接读 program header，不依赖 `file`/`ldd`：

| 检查项 | iip-server | iip-worker |
|--------|-----------|-----------|
| ELF64 小端格式 | PASS | PASS |
| `e_machine = EM_X86_64` | PASS | PASS |
| **`PT_INTERP` 缺失**（无动态加载器） | PASS | PASS |
| `PT_DYNAMIC` 缺失 | PASS | PASS |
| 无 `libc.so` / `libpthread` / `libdl.so` / `ld-linux` 引用 | PASS | PASS |
| 版本串 `0.0-m0-v1` 已注入（`-ldflags` 未静默失效） | PASS | PASS |

> `PT_INTERP` 缺失 + 无 libc 引用 = **真静态链接**。这是 distroless/static
> 能跑起来的前提；若这里是动态链接，镜像会在启动瞬间报
> `exec format error` 或 `no such file or directory`。

### 3.4 迁移 SQL 嵌入校验

| 检查项 | iip-server | iip-worker | 说明 |
|--------|-----------|-----------|------|
| 迁移文件名 `0001_init.up.sql` | PASS | 不存在（预期） | |
| `schema_migrations` 版本表 | PASS | 不存在（预期） | |
| `CREATE TABLE alerts` | PASS | 不存在（预期） | |
| `CREATE TABLE incidents` | PASS | 不存在（预期） | |
| `chk_alerts_status` 约束名 | PASS | 不存在（预期） | |

**为什么 worker 里没有迁移 SQL 是正确的**：

`store.Migrate` 只在 `cmd/iip-server/main.go:155` 被调用，worker 从不调用它。
Go 链接器的死代码消除（dead code elimination）会把未被引用的
`store.Migrate` 及其 `iofs` 依赖整体剥离，因此 `//go:embed` 的
迁移 SQL 数据不会进入 worker 二进制。

这是**正确且更优**的结果 —— worker 本来就不该有建表能力，
剥离后体积也更小（8.77 MB vs 11.19 MB）。
我用 `go list -deps` 交叉验证了依赖树，确认 worker 的 store 依赖
只保留 `Connect`/`HealthCheck` 路径。

## 七、本轮发现的缺陷与处置

### 7.1 已修复（产品代码，首轮）

| # | 缺陷 | 根因 | 处置 |
|---|------|------|------|
| 3 | `--healthcheck=false` 报 `unknown flag` | `wantsHealthcheck` 判「不触发」后落到 `config.Load`，但 flagset 未注册该 flag | 在 `internal/config/config.go` 注册 `healthcheck` bool；修后正确落入正常路径，报 `PGURL 必填`（应有行为） |
| 4 | `-ldflags "-X main.version=..."` 静默失效 | `main.version` 变量**根本不存在**，链接器不报错但版本号永远注不进去 | server / worker 各声明 `var version = "dev"` 并在启动日志输出；本次已实测注入生效 |
| 5 | **`iip-alertmanager` 恒为 unhealthy** | healthcheck 从 prometheus 复制而来，`grep -q Healthy`；但 alertmanager 的 `/-/healthy` 响应体是 **`OK`**，永远匹配不上 | 改为只依赖 `wget` 退出码：`wget -q -O /dev/null .../-/healthy`。见 `deploy/docker-compose.yml:110-119` |
| 6 | 国内网络下 `docker build` 必然失败 | Dockerfile 里 `go mod download` 走官方 `proxy.golang.org`，容器内直连超时 | Dockerfile 加 `ARG GOPROXY`（**默认值保持官方**，生产/CI 行为不变），本地验收传 `--build-arg GOPROXY=https://goproxy.cn,direct` |

> 缺陷 5 值得单独说明：它**只有在容器真正跑起来之后才能被发现**。
> 手工 `curl http://localhost:9093/-/healthy` 是好的，容器却报 unhealthy ——
> 断言与现象不一致，根因是「探针检查了别的东西」。这类缺陷在链路 A/B 阶段
> 结构上不可能暴露，是补测链路 C 的直接收益。

### 7.2 已修复（测试脚本自身，非产品代码）

| 问题 | 表现形式 | 处置 |
|------|----------|------|
| `echo "rc=$?"` 取错对象 | 报出的是上一条 `ls` 的状态，`go build` 的真实 rc 被掩盖，导致「假绿」 | 改用 Python `subprocess` 直接捕获真实 rc / stdout / stderr |
| `gofmt` 用错命令 | 调 `go fmt -l .`（`go fmt` 不接受 `-l`），得到 rc=2 却判成 PASS | 改用 `gofmt.exe -l .`，并加 rc!=0 判定 |
| 日志断言正则错 | 写 `version=0.0-m0-v1`（text handler 格式），实际是 JSON 的 `"version":"0.0-m0-v1"` | 修正正则 |
| 误判 worker 缺迁移 | 把 server 的检查项套到 worker 上 | 改为按角色区分检查项 |
| CHECK 约束假阳性 | INSERT 缺 `source` 等 NOT NULL 列，被 not-null 先拦下，根本没命中 CHECK | 补全所有必填列，让错误**只能**来自 CHECK |
| psql 输出解析错 | `-c` 会把命令标签 `INSERT 0 1` 一起输出，`out == 'firing'` 判断失败 | 新增 `psql_val()` 取第一行第一列纯值 |
| 表名列表写错 | 约束查询里误写 `integration_configs` 且漏了 `correlation_rules`，得数量 6 而误判 FAIL | 与迁移文件核对后修正为 7 张表的正确列表 |
| `terminate()` 是硬杀 | Windows 上 `Popen.terminate()` = `TerminateProcess`，Go 收不到 SIGTERM，drain 不被触发 | 改用 `CTRL_BREAK_EVENT` 投递真信号，**成功验证 drain 逻辑** |
| `port_free()` 名实不符 | 函数名说 free，语义是 in_use | 改名 `port_in_use()` |
| **容器名硬编码成服务名** | `docker exec postgres ...` 报 `No such container`：compose 里服务名是 `postgres`，但 `container_name` 是 `iip-postgres` | 新增 `svc_container()`，用 `compose ps -q <svc>` 取真实容器 ID；两条 postgres 断言由「假红」转 PASS |
| **等健康不等终态** | 只在 `iip-server=healthy` 就 break，此时 alertmanager 还在 `starting`，**漏掉了它随后变 unhealthy** | 改为「无任何服务停留在 starting/created」才算收敛，并新增「无 unhealthy」断言。缺陷 5 就是这样被暴露出来的 |
| **docker 定位逻辑写了两份** | `verify-images.py` 与 `prepull-mirror.py` 各自探测 docker.exe 与 cli-plugins，改一处漏一处 | 抽出 `scripts/lib_docker.py`，两个脚本共用一套定位规则 |

### 7.3 误判后纠正

| 我一度认为 | 实测结论 |
|-----------|---------|
| `go build -o /out/xxx` 在 `/out` 不存在时会失败，是 Dockerfile 缺陷 | **误判**。实测 `go build -o` 会自动创建父目录，rc=0。已加 `mkdir -p /out` 仅为可读性，非 bug 修复 |
| 手改 `%USERPROFILE%\.docker\daemon.json` 加镜像源即可生效 | **在 Docker Desktop 下不生效**。它以 GUI 里的配置为准，会把该文件回写覆盖（核对写入前的备份发现备份本身就是单源内容）。要加多源必须在 GUI 的 Docker Engine 编辑器里改。结论：**不要把验收建立在镜像源上**——「预拉取 + 重打标签」才是稳的路径（本次构建零网络即证明） |

| 项 | 状态 | 原因 |
|----|------|------|
| Alertmanager UI 可见 firing 告警 | **未验证** | 需构造告警触发条件，属 M4 证据采集范围 |
| `go test -race ./...` | **UNVERIFIED** | 本机缺 gcc（Windows 下 `-race` 需 CGO）；由 CI（ubuntu-latest 自带 gcc）覆盖 |
| CI 双 job 真实结果 | **待观察** | 用户裁决不推远端 |
| linux/arm64 镜像实机运行 | **未验证** | 仅验证了 linux/amd64。Dockerfile 已支持 `TARGETARCH` 覆盖，但未在 arm64 实机跑过 |

### 原阻塞根因（已解除，留档）

首轮链路 C 全项 BLOCKED，根因是 Docker Desktop 的 WSL2 后端从未安装。当时的决定性证据：

1. `WslService` / `vmcompute` / `LxssManager` / `com.docker.service` **全部 NOT INSTALLED**
2. Docker Desktop 安装日志 `install-log.txt` 中 `Selected backend mode:` **值为空** —— 安装时未检测到任何后端
3. `com.docker.backend.exe.log` 里 `State:stopped`、`StopReason:`（空）—— 引擎**从未被启动**，不是崩溃
4. `C:\ProgramData\DockerDesktop\` **不存在**（该目录仅在首次成功启动引擎时创建）
5. `wsl.exe` 存在，但执行时被沙箱 Program Blacklist 硬拦截 —— 反证后端必须是 WSL2
6. 当前进程 **非管理员**（`IsAdmin = False`），无法 `dism` 启用功能

**解除动作**：以管理员身份安装 WSL 运行时本体（`wsl.2.7.14.0.x64.msi`，SHA256 校验通过），
再由用户从开始菜单**手动**启动 Docker Desktop。

注意这里有一个预期外的结果：解除阻塞后链路 C **并没有自动全绿**。
它当场暴露了第七节 7.1 的缺陷 5（alertmanager 健康检查）与 7.2 的两项脚本缺陷，
修复后才达到 51 项全 PASS。这说明链路 A 的预验证只覆盖了「代码与构建」这一层，
容器编排层（healthcheck / 容器命名 / 依赖收敛）必须真跑才能验。
