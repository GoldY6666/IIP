## 2. 交付内容总览

### 2.1 告警接入与持久化（核心 M1）

- **五阶段管线**：`Validate → Normalize → Fingerprint → Deduplicate → Persist`（见 `internal/alert`）。
- **接口**：`POST /api/v1/alerts/webhook`，兼容 Alertmanager webhook payload（`version`/`groupKey`/`alerts[]`）。
- **去重/幂等**：唯一索引 `uq_alerts_fingerprint_firing` + `ON CONFLICT … DO NOTHING`；第二条同指纹 firing 静默跳过（影响 0 行）。
- **resolved 生命周期**：resolved 投递更新原行 `status='resolved'`、`ends_at` 非空；重起火后再次 resolved 仍正确（ADR-007 修复，见 §7）。
- **孤儿 resolved**：未知指纹的 resolved 跳过，不插孤儿行。
- **故障/边界**：停库 503、连接池关闭 503、超 1MB 413、非 JSON 400、缺 `version` 400、错方法 405、空 `alerts[]` 仍 200。
- **自动迁移**：启动执行 `migrations/`（0001_init + 0002 唯一索引），`healthz` 真实查库（`SELECT 1`）。

### 2.2 告警列表（本次新增切片，`a0ca8a5`）

- **后端分层**：`sqlc ListAlerts`（`internal/db/queries/alerts.sql` 新增 `ListAlerts :many`）
  → `Repository.List`（`internal/repository/alerts.go`）
  → `Service.List`（`internal/alert/service.go`）
  → handler `AlertList`（`internal/api/alert_list.go`，100 行）。
- **路由**：`cmd/iip-server/main.go` 新增 `GET /api/v1/alerts`。
- **分页与夹紧**：默认 `limit=100`、`max=1000`、`offset≥0`；参数缺省或越界（如 `limit=99999&offset=-5`）**降级为默认值而非返回 400**，保证前端联调不中断。

## 3. 技术设计要点

- **分层架构**：`api`（handler）→ `alert`（service/domain）→ `repository` → `db`（sqlc 生成）→ `store`（pgxpool）。依赖只向下，入口只装配零业务。
- **契约**：JSON snake_case、嵌入式结构体字段扁平化；时间 RFC3339。
- **限流**：`http.MaxBytesReader` 限制 body（`>1MB` → 413），避免大 payload 打爆内存。
- **指纹**：标准库 `crypto/sha256`，排除键写死四键（与 V1.0 一致）。
- **无新增第三方依赖**：`go.mod` require 仍为 chi / golang-migrate / pgx / koanf / pflag；M1 仅用标准库实现指纹与限流。

**本轮实测发现并修复的缺陷（ADR-007）**：`GetAlertByFingerprint` 原按 `ORDER BY starts_at DESC LIMIT 1` 取最新行；但 Alertmanager 重发同一告警时 `startsAt` 完全相同，并列时返回哪行**未定义**，导致 resolved 被误判为「重复 resolved」而跳过、告警永远停在 firing。已改为 `ORDER BY starts_at DESC, id DESC`，新增回归用例 `TestRefireThenResolveUsesLatestRow`（去掉 `id DESC` 立即转红）。
