### 5.1 A1–A4：计划文本与实测 schema 的四项偏差（已写入手册）

| 代号 | 计划文本的说法 | 0001/0003 的实测 | 处置 |

| **A1** | 状态含 `acknowledged` | 实为 **5 个小写值**，无 `acknowledged` | 沿用小写，新增 `acknowledged` 由 0004 重建为 6 值 |
| **A2** | timeline 7 个事件类型 | 实为 **5 值**，计划的 7 个一个都不在 | 既有 5 值保留 + 新增 7 个（0004 重建为 12 值）；事件创建复用既有 `alert_fired` |
| **A3** | `needs_review` / `correlation_score` 在 `incidents` 上 | 实际在 **`incident_alerts`**（关联边）上 | 读取口径按关联边实现（手册 §4.4） |
| **A4** | 错误体是 `{code, message}` | 实为 `{"error":"..."}` | 扩展为 `{error, code}`，`code` 缺省则不出现，向后兼容 |

这四项**不是实现缺陷**，是「M3 计划文本写得比实际 schema 乐观」；照计划直接写代码会四处踩空。

### 5.2 状态模型的实现口径（唯一真源）

```
ladder = [open, acknowledged, investigating, mitigated, resolved, ignored]   // 索引 0..5

CanTransition(from, to):
    if from == to:                  return false   // 同状态不算转换
    if from ∈ {resolved, ignored}:  return to == open    // 终态只能重开
    if to == open:                  return false   // 非终态不能回到 open
    return index(to) > index(from)                 // 只许前向
```

要点：只许前向不许回退；允许越级前向（如 `open → mitigated`）；`ignored` 置于阶序末端，
使「任意非终态 → ignored」天然成立；终态之间不可互转，只能经 `open` 重开。

V1.0 §6.2 原表在 `| INVEST |` 处被截断且带 `(AI生成)` 标记——**手册是该表的权威补全**，
此后以手册为准。非法转换统一返回 **422**，文案须含 `from` 与 `to` 两个状态名，便于前端直接展示。

`ignored` **不写** `resolved_at`（它不是恢复完成，写入会污染 MTTR 统计）；
代价是「忽略时刻」只能从 timeline 取。

### 5.3 本阶段实测发现并修掉的两处「脚本侧缺陷」

都是验收 / 联调脚手架的问题，**产品代码零改动**，但都伪装成产品故障：

1. **容器链路缺「干净起点」，第二次执行必假 FAIL**
   `compose down` 不加 `-v`，named volume 留着上轮告警 → 历史共现把 historical 维从 0 喂到约 0.534
   → 4.5.10 依赖维得分由 0.7133 抬到 **0.7667**，越出 `[0.70, 0.73)`。
   识别特征：容器里 `alert_id` 从 13 起而不是 1 起。
   **修法是加 TRUNCATE，不是放宽区间**：新增 4.5.0，迁移后投递前
   `TRUNCATE incident_alerts, alerts, incidents, correlation_feedback CASCADE`
   （保留种子行；CASCADE 不可省）。修复后在**同一份脏数据**上复跑，
   得分精确回到 0.7133、34 项全绿。

2. **手工投递 webhook 的两个必填字段**
   顶层 `version` 必须是 `"4"`（否则 400）；每条告警的 `status` 只能是 `firing` / `resolved`
   （否则 HTTP 仍返 200，但落进 `rejected` 数组）。
   → **判断投递是否成功要看响应体的 `accepted` / `rejected`，不能只看 HTTP 200。**

精确落到同一个 incident，`correlation_score = 0.7133`，与手册理论值一致——
这是 M2 关联引擎在真实环境里按设计工作的取证。

### 7.2 需要如实说明的环境约束

- **宿主机裸跑的进程活不过一次工具调用**（vite dev server 也一样），
  所以面向人工查看的前端只能走容器托管。
- 前端 `API_BASE` 是**相对路径** `/api/v1`，dev 模式靠 vite proxy 转发；
  改用静态托管后 proxy 消失，浏览器会直接请求 5173 端口 → 静态服务器回 404，
  表现为「页面打得开、列表一条没有」，**很容易误判成后端坏了**。
  现用 Go 标准库写的微反代容器（静态 + `/api` 反代 + SPA fallback）补上这一层；
  只用标准库，因此 `GOPROXY=off` 也能构建，全程零网络。

### 14.4 本批踩到并已修正的事（如实记录）

1. **真库门禁根本跑不完 —— 根因是 `CREATE DATABASE` 恒定 35 秒，且调参无效。**
   - 现象：两次运行分别撞 go test 默认 10m 与脚本 40m 上限，均非断言失败；
     且因文件按字母序执行，**我新写的用例一次都没真正跑过**（只在无库组被 SKIP）。
   - 拆解（`_diag_pg.txt`）：`CREATE DATABASE` 34.9s + 迁移 10.4s + `DROP DATABASE` 15.3s ≈ 60s/条，
     与实测单条 63.4s 吻合；残留库只有 2 个、全部库仅 46MB，**排除垃圾堆积**这个最初的猜测。
   - 调参**无效**（`_pg_tune.txt`）：`fsync=off` / `synchronous_commit=off` / `full_page_writes=off`
     后仍是 36.17s。瓶颈是 Windows 上逐文件复制 `template1` 的成本，属环境固有开销。
   - 修法（`_pg_schema.txt`）：`testsupport.NewDB` 改为「共享 session 库 + 每用例一个 schema」，
     靠连接串带 `search_path` 让迁移落进用例 schema，**4 个迁移文件一行未改**。
     `CREATE SCHEMA` 0.6s / `DROP SCHEMA` 2.1s → **61.2s/条 降到 13.1s/条（快 4.7 倍）**，
     repository 包由 31 分钟降到 7 分钟。隔离性由 `TestSchemaIsolationBetweenCases` 用真库断言，不靠推理。
   - 附带修正：残留 schema 的清理放在**脚本侧**（起库后、跑测试前），因为 go test 并行跑多个包，
     若由测试进程自行清理会删掉别的包正在用的 schema。
   - `postgresql.conf` 已还原（调参既然无效，不留 `fsync=off` 这种不安全的默认值）。

2. **我写错两条断言，产品代码没问题。** 必须分开说清楚：
   - `TestSchemaIsolationBetweenCases`：期望「schema 内 8 张表」，实为 9（漏算 0004 的 `review_suppressions`）。
     已改为断言**关键表名清单**而非张数，将来加迁移不会再无谓变红。
   - `TestLifecycleReviewRejectUnlinks`：断言「队列应为空」，实际剩 1 条 ——
     我漏算了 `other` 事件那条边（本次删的是 `(inc, shared)`，`(other, shared)` 理所当然还在）。
     已改为断言「只剩 `(other, shared)` 一条」，并把打印改成 `(incident, alert)` 对，
     只打印 alert id 会让人误判。

3. **handler 测试的分页夹紧契约表述错了**：我一开始断言 `ReviewList` 把脏参数退化成默认值，
   实际夹紧在**服务层**（`ListReviews` 的归一化），handler 只负责「解析不了就传 0」。
   已按真实分层修正断言，并在注释里写明两层各管一段。

4. **第一次超时把上一轮的报告文件覆盖写掉了**：脚本两轮写同一个输出路径。
   本期靠中途提取的关键行（`_m3_s2_head.txt` / `_m3_s2_hits.txt`）保住了证据，
   但这是脚本缺陷，应改为按轮次分文件落盘。
