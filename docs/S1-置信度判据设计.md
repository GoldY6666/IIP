## 一、这份文档解决什么问题

M4 留了一条 OPEN：`evidence.confidence` 全为空（`OPEN-M4-1`）。
理由当时是对的 —— 采集器并没有「这条证据有多可信」的判断能力，填 1.0 是撒谎。

但「一直留空」不能作为终点。手册 §4.3 要求它**随证据强度变化**，
所以 M6 S1 要做的是：**在采集器真的能给出来源时才填，且填出来的值必须可复核。**

判据设计的第一性问题不是「填什么数」，而是**「什么情况下有资格填」**。

## 二、三态而不是两态（最容易搞错的一处）

第一版想把情况分成「可评估 / 不可评估」两种。**这是错的。**

| 状态 | 含义 | 页面上显示 |
|------|------|-----------|
| `BandUnassessable` | 压根没法评估（缺基线、数据坏） | **不显示置信度** |
| `BandWeak` | 评估了，变化幅度不足 2 倍 | 显示低值 |
| `BandMedium` | 变化 2–5 倍 | 显示中值 |
| `BandStrong` | 变化 ≥ 5 倍 | 显示高值 |

若把 Unassessable 并进 Weak，「没有基线可比」会被读成「评估结果很弱」——
**把缺数据说成了负面结论**。这是两种完全不同的事，页面上必须能区分。

## 三、单一来源：规则命中 + 覆盖度（两个来源，不是三个）

**明确不采用「来源自带」**（如 Prometheus/Loki 的置信区间）：
本项目根本没取那些区间，写进 metadata 是编的。

两个来源都是本项目真有的：

### 3.1 规则命中强度（单条级，`Assess`）

读该条证据自己的 `Metadata`，四步判据，**顺序不可调换**：

| 步 | 检查 | 结论 |
|----|------|------|
| 1 | `baseline` 键**存在** | Unassessable |
| 2 | `change_ratio` 缺失 / 非数字 / 空串 | Unassessable |
| 3 | `change_ratio` 是 NaN 或 ±Inf | Unassessable |
| 4 | 其余按倍数落Weak/Medium/Strong | Weak/Medium/Strong |

**第 1 步为什么必须在最前**：`ratio()`（`collectors.go`）在分母为 0 时返回 **0** 而非 +Inf。
若不先看 `baseline` 就读 `change_ratio`，「没有基线可比」会被算成
「变化为 0 ⇒ 弱证据」。这是本项目已经踩过的「把缺数据序列化成零值」的形态。

**第 3 步为什么两种都要拒**：`formatFloat` 对 NaN/±Inf 返回的是**字符串**
`"NaN"` / `"+Inf"`（`ParseFloat` 直接失败，步2 已拦）；
但若某个采集器改用 `strconv` 格式化，就会得到真正的 ±Inf 数值 —— 步 3 兜这个。

**NaN 必须单独判**（`isNotFinite` 里`f != f`）：
NaN 的任何比较都返回 false，若漏判，`ratio >= StrongRatio` 会一路落到
default 变成 `BandWeak` —— **「数据坏掉」被静默解释成「变化很弱」**。

阈值：`MediumRatio = 2.0`、`StrongRatio = 5.0`
（5 倍取自手册 §4.1 原文例子「错误量 5 倍突增 ⇒ 高」）。

### 3.2 覆盖度（事件级，`Assign`）

统计**同一事件命中了几种证据类型**。分母固定 6。

**分母为什么固定 6**：可复核性要求分母是常数。
若取「当前已注册采集器的类型数」，关掉 k8s 采集器会让同一批证据的
置信度凭空变高，而数据一条没变 —— 那是配置漂移冒充质量提升。

代码里写成 `var CoverageTotal = len(evidence.SortedTypes())` 而非手写 `6`，
是为了将来 `CHECK` 约束加了第七种类型时不至于静默失真；
`TestCoverageTotal_MatchesEvidenceTypes` 是它的漂移守卫（双重断言：
等于 `len(SortedTypes())` **且**等于 6）。

**覆盖度只数「可评估」的类型**：不可评估的证据既不贡献覆盖度，也不进分母 ——
否则「采到 3 条但全无基线」会被算成覆盖度 3/6。

### 3.3 两级架构（偏离原方案的一处，必要）

原方案说「五个采集器在 `Collect` 末尾调 `rca.Assign`」。**这是错的**：

- `Assign` 需要跨采集器的覆盖度
- 每个采集器只知道自己这一类，算不出覆盖度

所以改成两级：`Assess`（采集器层，判单条强度）+ `Assign`（**编排层汇总后调一次**）。
落点：`internal/worker/processor.go`（F3 接线时实施）。

## 四、档位表

```
覆盖度命中类型数 → 基础置信度
  1 → 0.45    2 → 0.60    3 → 0.75    4 → 0.90
```

合成规则（`Compose`，三条）：

| 档位 | 结果 |
|------|------|
| `BandUnassessable` | **0, false** —— 调用方必须保持 nil，不得写 0 |
| `BandWeak` | `min(base, 0.50)` |
| `BandMedium` | `base` |
| `BandStrong` | `min(base + 0.05, 0.95)` |

**为什么弱档要封顶 0.50**：一条「变化不足 2 倍」的证据，无论同事件还有多少
其他类型的证据，都不该把置信度推到 0.9 —— 那等于让一条噪声去代表整批证据的强度。

**为什么单类命中取 0.45**（< 0.5）：让「未评估（nil，不显示）」与
「评估为 0.45（显示低值）」在**语义和视觉上都不会混淆**。

## 五、根因建议：只建议，不写库

手册 §2.2 把「自动写 `root_causes`」列为明确不做。本实现遵守：

- `SuggestFrom` 只返回建议，**不碰数据库**
- 只用**有置信度**的证据；`Confidence == nil` 说明「没有可复核来源」，
  拿它推断根因等于把缺数据当证据
- 每条假设必须列出支撑它的证据类型 —— 否则这就是一个不可证伪的结论
- 7 条**固定模板**而非自由文本生成。理由：每条可追溯到具体证据类型、
  措辞稳定（前端可按类型高亮）、不会出现「看起来很有道理但无从复核」的句子

**口径分离**（实现期修掉的一个设计缺陷）：

|字段 | 口径 |
|------|------|
| `Confidence` | **整批命中的类型数**（覆盖度 —— 这批数据整体有多可信） |
| `Support` | **该模板要求的类型**下的证据条数（这条假设有多少支撑） |

早先版本误用 `len(RequireAll)` 当覆盖度，导致
「命中 metric+log+deployment 三类」与「命中 metric+log 两类」算出同一个 0.60 ——
多命中的那一类被白白丢掉。覆盖度一旦被模板绑架，
「证据类型越多越可信」这条最基本的规律就不成立。
判据：`TestHypothesis_ConfidenceOrderedByCoverage`。

## 六、判据有效性：变异测试 8/8

判据全绿**不能证明判据有效** —— 一个从不赋值的实现也能让
「Confidence 非 nil 时取值合法」这类弱判据全绿。
所以做了变异测试，脚本 `D:\_iip_setup\_f2_mut_test.py`，报告 `D:\_iip_setup\_f2_mut.txt`。

### 6.1 六个正向靶点（期望红）

| 靶点 | 变异 | 实际变红的判据 |
|------|------|---------------|
| M1 | 恒填 0.45 | `TestAssign_VariesWithStrength` |
| M2 | 去掉 WeakCap | `TestCompose_WeakIsCapped` + `TestAssign_VariesWithStrength` |
| M3 | 摘掉 baseline 检查 | `TestAssess_BaselinePresentMeansUnassessable` |
| M4 | 摘掉 NaN 判断 | `TestAssess_NaNFloatIsRejected` + `MissingOrBadRatio` + 子用例 |
| M5 | 摘掉幂等保护 | `TestAssign_IsIdempotent` |
| M6 | 破坏覆盖度单调 | `TestCompose_CoverageLadder` + `StrongBonusCappedAtMax` |

**M1 是本组的核心靶点。** 早先写的是「摘掉赋值」，那样 Confidence 恒为 nil，
弱判据也能抓到。真正的危险退化是「所有证据都填同一个数」——
只有「值必须随强度变化」这条判据能抓它。

### 6.2 两个反向靶点（期望全绿）

R1 改 `joinTypes` 分隔符、R2 改 `Basis` 措辞 —— 都不改变语义，实测全绿。
反向靶点的作用是确认判据**没有过度敏感**。

### 6.3 变异测试自身的三个坑（实测踩到）

1. **提取器切片错位**：手写 `s[len('--- FAIL:'):]` 时前缀长度数错一位
   （实测 `'--- FAIL:'` 长度是 **9** 不是 10），把测试名首字母切掉，
   提取出空串且**不报错** —— 表现为「所有靶点都 BAD」但 `rc=1` 确实红了。
   修法：`removeprefix(...)` **之后先 `.strip()` 再 `split()`**。
2. **编译失败 ≠ 判据变红**：M1 初版写成 `_ = v`，导致 `v` 未使用而
   `[build failed]`。两者都是 `rc!=0`，只看 rc 会把**变异写法缺陷**
   误判成「判据生效」。修法：单独判 `[build failed]` 并标为 BAD。
3. **靶点必须破坏被验的不变量**：M6 初版把 `3→0.85 / 4→0.86`，
   看似破坏单调其实**仍单调**（0.85<0.86），打红的是
   `StrongBonusCappedAtMax`（破坏了 `4+bonus==Max` 等式）而非声明的
   `CoverageLadder`。改成 `4→0.70` 才真正破坏单调。

### 6.4 还原校验

变异必须**字节模式**读写 —— 文本模式 LF→CRLF，还原后 git 仍显示 M。
判据是还原后比 `sha256`：本次 4 个文件全部 sha256 一致。

## 七、k8s 采集器的可评估性（F3 前已修正）

**初版结论**：k8s 采集器不写 `change_ratio`（写的是
`occurrences` / `matched` / `rollout_ok` / `replicas` / `ready`），
trace 采集器不写任何可比字段 → 两类恒为 `BandUnassessable`。
已登记为 `OPEN-M6-2`。

**修正后（2026-10-07）**：k8s 的两类证据处置不同，不可一概而论。

| 证据 | 可评估性 | 依据 |
|------|---------|------|
| Warning 事件 | **可评估**（有 `change_ratio`） | 事件自带时间戳，能回溯到事故前 |
| rollout | **不可评估**（写 `baseline` 说明键） | K8s API 不保留历史副本数 |
| trace | 不可评估 | 无可比字段（未处理） |

### 7.1 Warning 事件侧为什么能算

`k8s.go` 对 events 只发**一次**请求（`fieldSelector=type=Warning`，
无 `limit`），时间过滤全在客户端做——所以「事故前有没有同类事件」的
数据本来就在手里，只是被单桶过滤丢掉了。改成两个桶是纯客户端改动：
零额外 IO、超时面与RBAC 权限。

实现见 `internal/collectors/k8s_baseline.go`。

| metadata键 | 含义 |
|------------|------|
| `matched` | 事故窗口内的真实命中数（**TopN 截断前**） |
| `matched_before` | 基线窗口（`[Start-width, Start)`）的命中数 |
| `change_ratio` | `matched / matched_before`，仅在 `matched_before > 0` 时写 |
| `novelty` | `matched_before == 0` 时替代 `change_ratio`，说明是新出现 |

> ⚠️ **`change_ratio` 在事件侧的语义是窗口级**，不是「这一条事件的变化倍数」。
> 同一批 Warning 事件证据上的该值相同（都等于窗口总量之比）。
> 与 prometheus 的「每个指标一个倍数」、loki 的「每个错误模式一个倍数」
> 不同——k8s 事件侧没有「按模式聚合」这一步，因为 Warning 事件已由 K8s
> 自己按 `involvedObject` + `reason` 聚合（`e.Count`）。
> 误读成单条强度会让「20 条里每条都强 5 倍」这种表述出现在页面上。

`matched_before == 0` 时**不给倍数**：`ratio()` 分母为 0 返回 0，
而「变化 0 倍」会被读成「强度很弱」，实际含义是「压根没有可比数据」。
同一情形在 loki 的错误模式证据里也是这么处理的。

### 7.2 rollout 侧为什么给不出

`Deployment` 对象只有**当前**副本数（`spec.replicas` / `readyReplicas` /
`updatedReplicas`），**K8s API 不保留历史值**。算「变化倍数」需要一个
事故前的副本数，而那个数不存在。

所以 rollout 写 `baseline` 说明键、**不写** `change_ratio`，
落进 `Assess` 第①步：

```
"baseline": "K8s API 不保留 Deployment 历史副本数，无法给出基线"
```

若不写这个键，`Assess` 会落到第②步，basis 说
「缺少 `change_ratio`，无法判断变化幅度」——**那把「设计上给不出」
说成了「采集器忘了写」**，运维会去查采集器代码而不是查集群。

判据第①步（`baseline` 键存在即基线不可用）本来就是为这种情况准备的，
但 k8s 采集器此前从未用过它。

### 7.3 仍然存在的落差（必须如实告知使用者）

模板「部署变更与指标突变在时间上重合」（`RequireAll = [deployment, metric]`）
在 k8s 证据上的触发条件是「**至少有一条可评估的 deployment 证据**」——
现在 Warning 事件可评估，所以该模板**可以触发**了；
但触发它靠的是事件侧的窗口倍数，不是「发布变更本身的强度」。

rollout 证据仍恒不可评估，trace 侧亦然。
`OPEN-M6-2` 因此**只被细化，未关闭**。

### 7.4 判据有效性：变异测试

脚本 `D:\_iip_setup\_m62_mut.py`，报告 `D:\_iip_setup\_m62_mut.txt`。
**正向靶点 6/6 变红，反向靶点 5/5 全绿**，两个被变异文件还原后 sha256 一致。

| 靶点 | 破坏的不变量 | 变红的判据 |
|------|-------------|-----------|
| M1b | 基线窗口紧邻事故窗口 | `TestK8sBaselineWindowDoesNotOverlapIncident` |
| M2 | 基线桶也过归属判定 | `TestK8sBaselineBucketAlsoFiltersOwnership` |
| M3 | 基线为 0 时不给假倍数 | `TestK8sEventBaselineZeroWritesNoveltyNotRatio` |
| M4 | 倍数随真实数据变化 | `TestK8sEventChangeRatioVariesWithData` |
| M5 | 分子用截断前的命中数 | `TestK8sTopNDoesNotPolluteRatio` |
| M6 | rollout 写 `baseline` 说明键 | `TestK8sRolloutExplainsMissingBaseline` |

M4 是**防退化实现**的关键靶点：只断言「有 `change_ratio`」的话，
一个把它写死成 `1.0000` 的实现会全绿。必须有一组用不同真实数据
算出不同倍数的用例（`0.2500` / `1.0000` / `4.0000`）。

反向靶点 M1 / M1c / M7 / R1 / R2 全绿，确认判据**没有过度敏感**：

- **M1**（`switch` → 两个独立 `if`）与 **M1c**（基线桶改闭区间）
  都是**等价改写**。「两窗不重叠」这个不变量被两套独立机制保护：
  `inWindow` 的半开区间 + Go `switch` 首个匹配即止（不贯穿）。
  单点变异打不穿是**冗余防御**，不是判据缺口——
  但也意味着这条不变量没有单点专属判据，靠 M1b（基线窗口位置）
  间接兜住。

### 7.5 变异测试自身的三个坑（本次实测踩到）

前两条与 §6.3 的「编译失败 ≠ 判据变红」同源，但形态更隐蔽：

1. **`-run` 正则带引号 ⇒ 一个用例都没跑**。用字符串
   `split()` 拼命令时，`"TestK8s|TestBaselineWindow"` 的引号会被
   一起传进去，Go 的正则匹配不到任何用例，输出
   `no tests to run` 且 **rc=0** —— **每个靶点都会绿**。
   修法：用列表传参；并把「被测集非空」写成脚本里的显式判据。
2. **`go test` 不带 `-v` 只输出一行 `ok`**，既无 `--- PASS`
   也无 `--- FAIL`。于是「提取失败用例名」得到空集、
   「被测集非空」判据恒假，43 个用例全跑全绿却被报成「判据无效」。
   修法：`-v` 必带；`ran_anything()` 显式判 `no tests to run`
   与 `--- PASS` 两个条件。
3. **汇总行按「实际 GREEN」计数会自相矛盾**：只数实际绿灯会把
   「正向靶点没变红」也算进「反向靶点全绿」，打出
   `反向靶点 4/3 全绿` 这种行。修法：按**期望**分类，
   分别输出 `bad_red` / `bad_green` 名单。

另有一条通用纪律：**靶点写错与判据失效必须区分**。
本次 M1 先被标成「期望红」但实际 GREEN，一度报成「判据无效」；
查下来是靶点本身是等价改写。反向操作也要做：把 M1c 这类
「单点打不穿」的靶点如实标成 `green`，而不是留在正向组里刷红。

**为什么 `Assign` 必须在截断之后**（变异靶点 M3 专门断这条）：
反过来会有两个错—— 覆盖度把已被砍掉的类型也数进去（页面显示 50 条证据、
覆盖度却写 4/6，人怎么算都对不上）；`Assign` 给随后被截断掉的证据白算一遍。

**为什么 `SuggestFrom` 只进日志**（禹 2026-07-07 裁定）：
自动写根因看起来聪明，但错的根因会误导处置且难以发现—— 与
`confidence` 填 1.0 是同一类错误。置信度有判据、可复核，根因没有。

### 9.2 三处已知的语义边界

| 边界 | 现状 | 处置 |
|------|------|------|
| **跨轮不重算** | 第一轮只采到 metric（覆盖度 1/6 ⇒ 0.50），第二轮才采到 log，那批 metric 仍是 0.50 | **接受**，登记为 `OPEN-M6-4`。`TestF3_CrossRoundDoesNotRecompute` 钉住这个语义 |
| **容器链路必然全空** | Loki `reject_old_samples_max_age` 默认 1h ⇒ 往 `[now-48h, now-24h)` 灌日志物理上会被拒 ⇒ 基线窗口 0 条 ⇒ 走 `baselineEmpty` 分支写 `novelty`/`burst` 而不写 `change_ratio` ⇒ `Assess` 第②步 ⇒全空 | 保持全空 + 加因果断言（§九.3）。**不改 compose** —— 为了让断言变绿去改被测环境，等于自己给自己签发合格证 |
| **k8s / rollout / trace 恒不可评估** | 见 §七 | `OPEN-M6-2` 未关闭 |

### 9.3 容器侧的五条因果断言（`verify-images.py`）

「全空」本身**不能区分**「`Assign` 没被调用」与「`Assign` 调了但输入不可评估」——
两种情况下都是全空。所以配了四条交叉验证：

1. 全空（`confidence IS NOT NULL` 计数 = 0）
2. 均无 `change_ratio` 键（基线窗口无数据，非采集器缺陷）
3. 有 `novelty`/`burst` 键的证据 `confidence` 为 NULL（未评估 ≠ 0）
4. **worker 日志里出现 `rca.Stats` 的 `confidence` 字段，且 `assigned=0` / `unassessable>0` / `coverage=0/6`** ← 最关键的一条：没有它，上面三条都可能是「`Assign` 压根没跑」
5. 无 `confidence_basis`/`confidence_coverage` 键（`Assign` 未覆写任何一条）

### 9.4 变异测试 3/3（`D:\_iip_setup\_f3_mutate.py`）

| 靶点 | 变异内容 | 期望 | 实测 |
|------|----------|------|------|
| M1 | `Compose`恒返回 `0.45` | 红 | ✅红，**7 PASS / 7 FAIL** |
| M2 | `processor.go` 不调 `Assign` | 红 | ✅ 红，**3 PASS / 11 FAIL** |

**M1 是核心靶点**：真正危险的退化不是「不赋值」（弱判据能抓到），
而是「所有证据都填同一个数」—— 只有「值必须随强度/覆盖度变化」能抓。

### 9.5 本轮实测踩到的两个坑

**坑1：变异测试用 `git checkout` 还原会吃掉未提交的工作改动。**
第一版脚本用 `git checkout --` 还原，跑完报「还原成功」，
但 `processor.go` 里本轮的全部改动被一起还原到了 **HEAD**（早于本轮改动）。
后续步骤里 `git status` 干净得像什么都没发生过—— **只有再跑一次测试
才发现文件内容不对**，那时已难以判断是何时丢的。
改为**施加变异前把原始字节存进内存，还原时字节写回**；
并额外做「还原后 sha256 与变异前一致」的有基准比较
（`git status` 那个检查在「本轮改动本来就未提交」的前提下**没有鉴别力**）。

**坑 2：mock 造不出区分度时，症状长得像产品算错。**
`verify-func.py` 的 `_prom_handler` 原按 `FIXED_START` 锚定返回 1 或 10，
但 `FIXED_START` 是**告警**时间窗而 worker 实际采集窗口是 `[now-24h, now]`
（`ResolveWindow` 会把过老的起点夹到 `maxLookback` 内），两者不是同一个区间
⇒ 基线查询与事故查询**都落在锚点之后** ⇒ 两边都返 10 ⇒ ratio 恒 1.0
⇒ 置信度恒为同一档 ⇒ 判据「取值种类 >= 2」FAIL。
**判据本身是对的**（`distinct=1` 恰好抓到了「值不恒定」），
是喂进去的数据没有区分度。改为锚在「较晚/较早」这个真实不变量上
（事故窗口 `End` 晚于基线窗口 `End`，见 `prometheus.go` 的
`before = {Start-width, Start}`），不再依赖任何具体日期。
**教训**：断言失败时先问「是判据错还是被测对象错」，
而「mock 与被测对象的坐标系不一致」是第三种可能。
