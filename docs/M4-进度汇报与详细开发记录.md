### 2.2 三个采集器的关键设计

| 采集器 | 采什么 | 必须这么做的理由 |
|--------|--------|-----------------|
| Prometheus | RED 指标**窗口前后**对比 | 采**两个窗口**（基线早于事故起点 2h，当前 = 事故区间）算 `change_ratio`；单点取值没有意义 |
| Loki | LogQL 错误日志 Top10 + 错误量突增 | 归一化日志模式后**聚合计数**——同一类 `db timeout` 采 5 次应聚成 `count=5` |
| K8s | Warning 事件 + Deployment rollout | 见 §2.3 缺陷一；**默认关闭** |

三者共有的硬约束：

- **`timestamp` 是证据自身的时间，不是采集时刻**；给不出真实时间**一律跳过**，
  不用 `NOW()` 兜底（ADR-003）。
- 单次采集失败**不阻断**其余采集器；全部失败才算任务失败。
- 超时 5s（`IIP_EVIDENCE_TIMEOUT`）。

**容器链路实测的 `evidence=7` 就是聚合逻辑正确的证明**：6 类错误模式各 1 条
+ 1 条「错误量突增」。若归一化把 6 条错误信息聚成 1 类，就只会剩 2 条。

### 2.3 过程中发现并修复的四处缺陷

**这一节是 M4 最有价值的部分。** 四处**全部由本阶段新写的测试抓出**，
每处都补上了能抓住它的测试。

#### 缺陷一：K8s 事件被挂到错误的服务上

- **现象**：`TestK8sServiceMatchIsNotSubstring` 抓出 `checkout-staging-1` 被算作 `checkout` 的事件。
- **根因**：用字符串前缀匹配判定服务归属。Pod 名形如 `<deployment>-<hash>-<suffix>`，
  而 Deployment 名由用户随意取——前缀匹配在真实集群里根本不可靠。
- **为什么严重**：等于把 A 服务的事故证据挂到 B 服务上，而**页面上完全看不出来**
  （证据条数正常、格式正常）。
- **修法**：两步判定，顺序不能换。① 先在**全命名空间范围内**为事件对象定出唯一主人
  （最长匹配）；② 再看这个主人是否属于本服务。
- **中间踩的坑**：最初只在「本服务的 Deployment 集合」内找最长匹配，而
  `checkout-staging` 不在这个集合里 → 最长匹配只落在 `["checkout"]` 上，
  `checkout-staging-5f8c` 仍被 `checkout` 认领。**先定主人、再判归属**才正确。

#### 缺陷二：K8s 采集器开关是死配置（最隐蔽）

- **现象**：`EvidenceK8sEnabled=true` 且地址已配时，装配函数**只打日志、从不注册**。
- **为什么严重**：用户打开开关、填好地址、日志显示「已启用」，但证据恒为 0 条，
  且**全程无任何报错**。用户没有任何线索知道该查哪里。
- **为什么 24 个单测全绿**：采集器的单测**全部用自己 `new` 出来的实例**，
  绕过了 `buildRegistry`——典型「替身验不了装配链路」盲区。
- **修法**：装配层真的注册；`config.Validate` 阶段拦下缺 URL / namespace 的组合；
  **补 `cmd/iip-worker/main_test.go` 的 3 个装配用例**。

#### 缺陷三：迁移单步回滚用例的断言随迁移总数漂移

- **现象**：全量真库门禁 4 条 FAIL，**产品行为完全正确，红的是测试本身**。
- **根因**：两处用 `Steps(-N)` 配合手写常量 `latestVersion = 4`。
  M4 新增 `0005`/`0006`/`0007` 后「退几步」语义漂移，**断言里的期望值也跟着漂**——
  于是用例转红，而被测的 0003/0004 的 down **从头到尾没被测过**。
- **更糟的是这类漂移不报错**：回滚落到了别的迁移，断言也跟着错，两者自洽，
  看起来只是一条红测试。
- **修法**：`Steps(-N)` → `mustDownTo(绝对版本)`；`latestVersion` 改为**从 embed 里数出来**
  的函数，删掉手写常量。
  > 手写版本号要求每个写迁移的人记得同步改一个数字，**而「记得」不是可验证的**。
- **教训**：这是「别把断言绑在会变的量上」的又一例。同一坑在 M3 踩过一次
  （「表数=8 因 0004 变 9」），**M4 又踩了一次**（§2.5 链路 B）。

#### 缺陷四：端到端判据 #3、#4 测了但没测到

| 判据 | 原实现为什么是假通过 | 修法 |
|------|-------------------|------|
| #4 恢复后自动补采 | 证据从 5→15 条是因为**新告警创建了新事件**；而 `tasks` 3→3、`done=3` 第一轮就满足了——**worker 从未重试过任何东西** | 改为断言 `attempts` 走 1→2→3，并检查**该事件**从 0 条变 5 条 |
| #3 webhook 延迟 | 第二次投的告警与前面那条**同指纹** → 被去重 `skipped`，**测的不是完整接入路径** | 换用不同指纹的告警名 |

修完后实测：`attempts` 1→2→3 走完，`status=done`，webhook 31ms→61ms。
**不修的话，这两条判据等于没验。**

### 2.5 门禁实测

| 链路 | 脚本 | 结果 | 耗时 |
|------|------|------|------|
| A 业务闭环 | `verify-func.py` | 75 PASS / 0 FAIL | 2 分 16 秒 |
| B 宿主全栈 | `verify-runtime.py` | 45 PASS / 0 FAIL | 2 分 57 秒 |
| C 容器链路 | `verify-images.py` | 59 PASS / 0 FAIL | 2 分 00 秒 |
| D 静态门禁 | build/vet/gofmt/golangci-lint | 四项全 rc=0，无 `nolint` | 61 秒 |
| E 前端构建 | `tsc -b` + `vite build` | rc=0 | 12 秒 |
| **全量真库门禁** | `m4_final_gate.py` | **425 PASS / 0 FAIL / 0 SKIP** | 22 分 30 秒 |

**SKIP=0 是硬要求**：真库门禁里出现 SKIP 等于「这一条根本没验」。

**两条必须 `-p 1`（包级串行）**——这是实测逼出来的，不是保险起见：
第一次全量跑时 `internal/repository` 的 88 条用例在 **1.4 秒内全部失败**，而单跑 10s/条全 PASS。
根因是 `go test ./...` 让多包并行，同时在同一 PG 实例上建 schema，**schema 级隔离被自己冲掉**。
这类快失败极具欺骗性（不像断言失败，更像「库连不上」），极易误判成环境问题。

**链路 C 不可省**：ADR-019 那个缺陷（compose 漏给 worker `IIP_PROM_URL`/`IIP_LOKI_URL`）
在 A/B/D/E 全绿的情况下**完全不可见**——裸跑测试用进程内假 HTTP 服务，
不读 compose 的环境变量。后果是 worker 静默跳过注册，事件永远采不到证据。

**链路 B 修掉的测试缺陷**：原断言 `public 表数量 == 8`，M4 加 `tasks` 表后变 10，
**产品正确而测试红**。已改为「总数只记录不判定 + 10 张关键表逐张断言」。
> 教训：同一文件里紧邻的上一行已是正确写法，**只有这一行漏了**——
> 两种风格并存比全错更糟，改对一处容易以为都对了。

## 4. 纪律与约定（继续沿用）

1. **实现与手册不符 = 缺陷**；任何偏离**先改手册再改代码**。
2. **未做项必须如实标注，不得写成通过**（AGENTS.md 约束 5/ 12）。
3. **不加 `nolint`、不新增排除规则**；lint 逐项修复。
4. **「我算错了吗」要排在「产品错了吗」之前**——M4 的缺陷三、四都是测试自己错。
5. **断言要落在属性语义上，不绑在会变的量上**（缺陷三、链路 B 表数）。
6. **「替身验不了装配链路」**——采集器单测全绿不等于装配正确（缺陷二）。
7. **验收链路要覆盖部署形态**（链路 C），否则静默降级类缺陷全绿通过。
